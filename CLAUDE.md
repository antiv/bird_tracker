# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Flutter app for bird watchers: record "transects" (survey routes) on a Google Map, drop markers for bird sightings with species data, attach photos to a record, export/share as CSV/KML/KMZ. Targets Android and iOS. Bundle IDs: `rs.antonijevic.bird_tracker` (Android), `rs.antonijevic.birdTracker` (iOS).

## Commands

Flutter is managed by **fvm** — plain `flutter` is not on PATH. Use `fvm flutter ...` (or `~/fvm/versions/stable/bin/flutter`).

```bash
fvm flutter pub get
fvm flutter run                 # dev run on connected device
fvm flutter analyze             # lint (flutter_lints defaults)
fvm flutter build ios --no-codesign   # verify iOS compiles
```

`fvm flutter test` runs three files in `test/`: the CSV/KML export contract (`export_roundtrip_test.dart`), the record form (`species_form_test.dart`), and the KMZ/backup archives (`media_archive_test.dart`). The two widget-test files pump `EasyLocalization` inside `tester.runAsync` — without that its translations never load and every `.tr()` comes back as the raw key; they also need `SharedPreferences.setMockInitialValues({})` before `EasyLocalization.ensureInitialized()`, which reaches for the plugin.

Three things bite when testing anything photo-related: `dart:io` futures never resolve inside `testWidgets`' fake async, so a temp media directory has to be created in `setUp`/`setUpAll` and `MediaService().init(root: …)` pointed at it; an `Image.file` whose file actually exists starts an image decode the test binding only finishes inside `runAsync`, so `pumpAndSettle` hangs forever if a thumbnail resolves; and the photo strip pushed the form's buttons past the default 800×600 viewport, so a tap on Save needs an `ensureVisible` first.

### Release builds

- **Android**: `./build_release.sh [--bump]` — cleans, builds obfuscated appbundle, copies to `bird_tracker.aab` at repo root. `--bump` increments patch+build in pubspec.
- **iOS**: `./deploy_ios.sh` — full build + signed export + upload to App Store Connect via API key. **Bumps version by default**; use `--no-bump` if the version was already bumped, `--no-upload` to only produce the .ipa. Requires `ios/deploy.env` (see `ios/deploy.env.example`). The script patches the generated SPM `Package.swift` from iOS 13 → 14 (required by file_picker) before building — don't "fix" that seemingly redundant sed.

Version format in pubspec.yaml is `X.Y.Z+N`; both scripts bump patch and build number together. Apple requires a new build number for every App Store Connect upload.

## Configuration / secrets (not in git)

- **`.env` at repo root** — bundled as a Flutter asset and required at runtime (`main.dart` crashes without it). Keys: `MAPS_API_KEY` (+ optional `MAPS_API_KEY_ANDROID` / `MAPS_API_KEY_IOS` overrides), `PRIVACY_POLICY_URL`. Consumed in three places: Dart via flutter_dotenv, Android via `build.gradle.kts` → manifest placeholder `${mapsApiKey}`, iOS via `AppDelegate.swift` which parses the bundled asset at runtime.
- **`android/key.properties`** — release keystore config for Android signing.
- **`ios/deploy.env`** — App Store Connect API key credentials for deploy_ios.sh.

## Architecture

Single-screen app: `lib/home_page.dart` hosts the Google Map and drives everything else through dialogs/bottom sheets.

- **State**: `lib/service/data_service.dart` — a ChangeNotifier **singleton** exposed through `provider`; holds the active `Transect`, map controller/completer, map type, and SharedPreferences accessors. Widgets call `DataService()` directly (factory returns the singleton) and `notify()` to trigger rebuilds.
- **Persistence**: `lib/service/sembast_service.dart` — sembast NoSQL singleton with a single `transects` store. Models are **manually JSON-serialized** (`toJson`/`fromJson`, no codegen). This replaced Isar; backup/restore lives here too. A backup is a **`.zip`** (`lib/utils/backup_utils.dart`): `bird_tracker_backup.json` at the root — byte-identical to the old plain-JSON backup — plus `media/` with the record photos. It is written and read with `ZipFileEncoder` / `decodeStream`, streaming photo bytes straight between the media directory and the archive — never buffer a whole archive, a season of field photos is hundreds of megabytes. Restore still accepts a bare `.json` so older backups keep working, and it is destructive by design: it wipes the store and then sweeps media files no restored record references.
- **Models** (`lib/model/`): `Transect` (route with start/end, name) → `points` (recorded track) + `markers` (`Placemark` sightings) → `Species` entries. `Transect` owns the CSV export and the share entry points; `lib/utils/kml_utils.dart` owns KML and `lib/utils/kmz_utils.dart` the KMZ wrapper around it. The species catalog is a hardcoded list in `lib/configuration/species.dart`.
- **Export formats**: CSV headers are hardcoded English, but the file is written as UTF-8 **with BOM** — species names and behaviour notes carry Serbian diacritics, and both exports used to go out through `.codeUnits`, which silently mangled them. KML carries the records as JSON in each placemark's `<ExtendedData>`; that payload, not the human-readable `<description>`, is what re-import reads, so any new record field round-trips as soon as it is in `toJson`. It sits in a **namespaced** `<bt:records>` (`kBtNamespace`) because a plain `<Data name="records">` is what viewers render as a name/value table, and they would print the raw JSON at the user. `kmlToTransect` **falls back to parsing the `<description>` prose** (`getSpeciesFromDescription` → `Species.fromSpeciesString`) when a placemark has no payload — that was the only round-trip mechanism before, so every KML already shared with a colleague still imports. `Transect.shareKML` emits a **KMZ** whenever a record photo is on disk and a plain `.kml` otherwise; a KMZ is a zip of `doc.kml` plus `files/`, and only then does `generateKML(photos: …)` swap the placemark description for CDATA HTML with `<img src="files/…">`. That argument is the exact list the archive bundles, so a record naming a photo whose file has gone missing keeps the name in `ExtendedData` — losing it would erase what was photographed — but gets no `<img>` and therefore no broken image in Google Earth. `Transect.hasPhotos` answers from memory alone because the history list calls it from an item builder every frame; `KMZUtils.availablePhotos` is the one that stats the disk, once, in `shareKML`. Import (`showImportDialog`) accepts both and decides which by **sniffing the zip magic**, never by the extension: share targets rename attachments freely. That subject and every export file name go through `sanitizeFileName` (`file_utils.dart`) — the transect name is free text and a `/` in it used to become a directory separator in the shared file's path, taking the extension with it. The picker uses `FileType.any` plus its own check rather than `FileType.custom`, because that maps extensions through Android's `MimeTypeMap`, which knows neither `kml` nor `kmz` and greys the files out. The `<img src="files/…">` balloon images only render in Google **Earth Pro** (desktop); the **web** builds of both Earth and My Maps parse the tags but never resolve a path into the archive, so photos read as broken there — nothing in the KMZ is wrong when that happens.
- **Photos** (`lib/service/media_service.dart`, strip UI in `lib/widgets/photo_strip.dart`): a record may carry several. Each one is stored twice — the canonical copy under `<appDocuments>/media`, which every thumbnail and every export reads, and a user-visible copy in the "Bird Tracker" gallery album via `gal`. A failed gallery write is not fatal, only the shortcut in Photos is lost. `Species.photos` holds **file names, never paths**: the iOS app container path changes between installs, so a persisted path would break. Photos hit the disk before the record exists, so `SpeciesForm` reconciles on save (files it no longer lists are deleted) and on dispose (files added and then abandoned are deleted) — never at the moment the user taps the ×, or cancelling would gut a saved record. `_clear()`, the "save and new" path, resets both lists so the next record cannot delete the previous one's files. The gallery copy is never deleted, the way a camera app behaves.
- **Deleting photos**: only the form deletes files on its own, and only ones no saved record ever owned. Deleting a transect, a point or a record goes through `showDeleteWithPhotosDialog` (`ux_builder.dart`), which adds an opt-in checkbox — **off by default** — for the photos that delete would orphan; without it the files stay. The checkbox copy says photos taken in the app survive in the gallery album but imported ones do not, and that is literally true: `MediaService.writeBytes`, the path a KMZ import and a backup restore take, never pushes to the gallery. Restore is the one place that still sweeps photos without asking, which is in character since it replaces the whole database anyway.
- **UI helpers**: `lib/utils/ux_builder.dart` — global dialogs/snackbars/bottom sheets using `context_holder` (`ContextHolder.currentContext`), so no BuildContext threading. All user-facing strings go through easy_localization `.tr()`.
- **Location**: uses the `location` package (not geolocator/permission_handler). The permission + background-mode flow is in `lib/utils/location_helper.dart`: a custom pre-permission dialog (`showPermissionInfoDialog`) precedes the system prompt, then `enableBackgroundMode()`. The dialog text is **platform-specific** (`Platform.isIOS` in ux_builder.dart) because Android needs a two-step "Allow all the time" grant while iOS does not. That second step is **not** the plugin's: `location`'s own `enableBackgroundMode` calls `requestPermissions([ACCESS_FINE_LOCATION, ACCESS_BACKGROUND_LOCATION])` in one go, and Android 11+ ignores any request that bundles background with foreground — no prompt, nothing granted, which is exactly how the "Allow all the time" step went missing. `ACCESS_BACKGROUND_LOCATION` is therefore requested alone, after the foreground grant, over a MethodChannel in `MainActivity.kt` wrapped by `lib/utils/background_location_permission.dart`; `ensureBackgroundPermission()` in location_helper runs it (rationale dialog → request → settings fallback) before handing off to the plugin, which then only starts its foreground service. It asks **once per app run** — `goToCurrentLocation` is also the my-location button, and a user who declined should not be re-prompted on every tap. On Android 11+ the request opens the app's location settings page instead of a dialog and returns empty `grantResults`, so the callback answers from a fresh `checkSelfPermission`, never from the result array. iOS keeps the plugin's flow: every channel call short-circuits to success there.

## Localization — keep three places in sync

1. **App strings**: easy_localization with `assets/translations/en.json` and `sr-Latn.json`; supported locales `en` and `sr-Latn`, fallback `en` (`lib/main.dart`). Any new UI string needs a key in **both** JSON files.
2. **iOS permission strings**: `ios/Runner/Info.plist` holds the English (default) `NSLocation*UsageDescription`, `NSCameraUsageDescription`, `NSPhotoLibraryAddUsageDescription` and `NSPhotoLibraryUsageDescription` values; localized overrides live in `ios/Runner/{en,sr-Latn,sr}.lproj/InfoPlist.strings` (registered as a variant group in project.pbxproj). If a permission string changes, update the plist **and all three** .strings files — Apple rejected the app once (Guideline 4) for permission prompts not matching the app's language.
3. **Android**: permission dialogs are system-provided; no strings to maintain.

A `.strings` value must not contain a raw `"` — Xcode fails the build with "Couldn't parse property list", pointing at line 0 of the file.

## Media permissions

Photos deliberately cost **no** sensitive permission. On Android `image_picker` takes photos through `ACTION_IMAGE_CAPTURE` (so no `CAMERA` — declaring it would only make Android start demanding it) and picks through the Android 13+ photo picker (so no `READ_MEDIA_IMAGES`, which Play does gate behind a declaration form). The manifest carries only `WRITE_EXTERNAL_STORAGE` with `android:maxSdkVersion="29"` plus `android:requestLegacyExternalStorage="true"`, both required by `gal` below API 29; capped that low it does not trigger Play's storage declaration, which targets `MANAGE_EXTERNAL_STORAGE`. What does need updating before a release is the **Play Data safety form** ("Photos and videos" — not collected, not shared, since nothing leaves the device except through the user's own share sheet) and the privacy policy behind `PRIVACY_POLICY_URL`.

On iOS the three usage descriptions above are mandatory or the build is rejected outright (ITMS-90683); `NSPhotoLibraryUsageDescription` is needed on top of the add-only one because `gal` writes into a *named* album. The App Privacy label stays "Data not collected" — Apple does not count on-device-only data as collected.
